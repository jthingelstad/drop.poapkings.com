# Infrastructure

`template.yaml` provisions the production Elixir Drop web application and API
as one CloudFormation stack:

- a private S3 web bucket behind a CloudFront origin access control;
- a retained private S3 bucket for permanent run, badge, and profile preview PNGs;
- one CloudFront distribution that serves static assets and sends `/api/*`,
  `/share/*`, `/share-assets/*`, `/updates/*`, and `/feed.xml` to the Lambda Web Function, plus a small
  request function for classification, viewer-IP forwarding, prefix, and
  directory-index rewriting;
- an ACM certificate supplied from `us-east-1`;

- one Arm64 Node 24 Lambda Web Function, with three environments, eight requests
  per environment, a 20-second timeout, and the minimum supported 100 RPS guard;
- an IAM-authenticated endpoint accessible only through CloudFront OAC
  (`always-amz-auth`), preserving bearer authorization through a zero-default-TTL cache
  policy. The edge overwrites viewer IPs; the origin resource policy explicitly
  denies requests from outside the distribution. The HTTP server owns CORS;
- DynamoDB on-demand table with point-in-time recovery, encryption, TTL, and a
  seasonal leaderboard index;
- an encrypted FIFO refresh queue (content-based deduplication) with a
  dead-letter queue and worker Lambda, plus the retained season-repair queue,
  dead-letter queue, and consumer;
- an hourly EventBridge Scheduler run (`elixir-drop-prod-war-clock`, :05 UTC) that
  queues the season clock job through its own send-only role, so a season
  finalizes without a visitor, a `WarClockSaved` metric from the worker's
  `war-clock.saved` log line (no alarm on it since 2026-11-03);
- a daily EventBridge Scheduler run (`elixir-drop-prod-run-analysis`, 11:15 UTC)
  that invokes the run-analysis Lambda directly. Its role may only Scan the
  table, projected to an attribute allowlist, and write the
  `/elixir-drop/run-analysis` log group (`docs/FAIR-PLAY.md`, "Run analysis");
  and
- a least-purpose Lambda runtime role for DynamoDB, SQS, logs, and the share
  preview bucket. It has no Bedrock grant: Drop makes no model call since the
  name, picture and tag come from Elixir (2026-11-14), and the `NameModelId`
  parameter and `NAME_MODEL_ID` variable went with the name generator.

The stack also exports a narrowly scoped leaderboard-maintenance role. The
`elixir-drop` deploy user may assume it for explicit data repairs; it can scan
the game table and update only `GSI1PK`/`GSI1SK` on `PLAYER#` items, so it cannot
change canonical runs, scores, profiles, XP, or referee evidence.

Player run reports are read through another exported role,
`elixir-drop-run-reports`. It can only query the `RUN_REPORTS` partition to
list identity-free reports; run-report triage, and the role's write, were
retired on 2026-11-02. It cannot scan the table, read player/account partitions,
or access a secret. Its trust policy names the same-account `elixir-drop` user
directly, so the ordinary stack deployment makes it assumable without an
administrator bootstrap refresh.

Player Updates use a dedicated bearer token generated by `npm run bootstrap:aws`
and retained in the root mode-0600 `.env`. The API holds its copy through the
runtime secret ("Runtime secret" below), so the two copies are kept equal by
hand. The Updates CLI and Control Room send that token directly to
`POST /admin/updates` over HTTPS, so routine publication has no AWS profile, STS
session, or interactive login.

The private fixed-host Control Room assumes two other roles. The referee role
remains pseudonymous and writes only `REFEREE#` overlays. The separate
`elixir-drop-control` account-support role can project an explicit allowlist of
profile and Clash snapshot fields (including email) and query the
`CONTROL#PLAYER#` audit events of corrections made before 2026-11-14. It writes
nothing: the name, picture and tag come from Elixir, and the public-profile
correction grant (`TransactWriteItems` on `PLAYER#` and `CONTROL#PLAYER#`) went
with the profile editor. Sign-in links, Elixir identity pointers, sessions,
run/evidence bodies, scores, XP, deletes, and secrets are outside the role. (The
grants Drop's retired Buttondown backfill used went with it on 2026-10-12.)

Drop sends no mail and keeps no mailing list (2026-10-12). Its email-code
sign-in, the `elixir-drop` SES configuration set, the `EmailFrom` parameter,
the Lambda's SES permission, and the Buttondown newsletter with its
`ButtondownApiKey`/`ButtondownNewsletterId` parameters are retired: a Drop
account is an Elixir account, and Elixir's one list is Elixir's. Deleting a
Drop account unsubscribes nobody from it. The bootstrap-owned execution role
keeps its now-unused grant on the deleted `elixir-drop` configuration set until
`npm run bootstrap:aws` next rewrites it.
CloudWatch alarms only on refresh queue age (`elixir-drop-prod-refresh-age`)
since 2026-11-03: the account keeps alarms only where someone acts on them,
and the other nine (API errors, p95 latency and throttles, DynamoDB
throttles, the web 5xx rate, the refresh and season-repair dead letters,
season-repair consumer errors and the stale season clock) were removed
(`docs/monitoring-retirement.md`). The API, refresh
worker, and repair consumer write JSON logs to dedicated 30-day log groups.
The operational alarm topic targets `drop@poapkings.com` by default.

HTTP logging uses the managed `/elixir-drop/api` and `/elixir-drop/api.local`
groups with 30-day retention. App timings include a bounded route template and
API build identity, never viewer IPs, raw paths, identities, tokens, or OAuth
queries. The stack owns no CloudWatch dashboard: since 2026-11-02 the `drop`
dashboard in Grafana on Otto (otto-ops) charts CloudFront, DynamoDB, and Web
Function requests/errors, CPU, active time, memory and concurrency, with route
counts and p95 queried from application logs. A log metric filter publishes
request latency to `ElixirDrop/HTTP`, and native Web metrics count HTTP 5xx and
throttles; no alarm watches them since 2026-11-03. The endpoint's
`MaxEnvironments` is 3 and ordinary page-load bursts reach it with no throttle
(`docs/monitoring-retirement.md`, issues #94 and #95).

CloudFront standard logging v2 writes JSON access records to the 24-month (731-day)
`/elixir-drop/web-access` log group. The delivery deliberately excludes viewer IP,
forwarded address, user-agent, referrer, cookie, query string, raw URI path, and
request ID. Instead, the viewer-request function contributes a bounded class for the
home page, each public static page, assets, card art, app metadata, discovery files,
the service worker, API traffic, and unknown requests. This makes cache outcomes,
status codes, edge detail, bytes, and time-to-first-byte useful without turning the
operational log into a player or visitor ledger. `node scripts/web-activity.mjs`
verifies delivery and retention, then returns only aggregate Logs Insights results.
Grafana charts CloudFront requests, bytes and error rate (no alarm since 2026-11-03).

`npm run bootstrap:aws` is the one-time setup. It uses the currently configured
administrator credentials to create the `elixir-drop` IAM deploy user, a
CloudFormation execution role, a private versioned code bucket, and a mode-0600
gitignored root `.env`. It copies the host-only card-refresh CR token only into
that local file; Lambda and CI never receive it. Regenerating `.env` removes
retired bridge credentials and queue names. Secret values are never printed.

`npm run deploy:api` then uses AWS SDK clients—not the AWS CLI—to build and zip
the TypeScript Lambda, upload it, create or update the stack, and write the
public API endpoint to `apps/web/public/api-config.json`.

After the web workspace builds, `npm run deploy:web` rewrites only the generated
`dist/api-config.json` to the same-origin `/api` base, uploads the build to the
private bucket with explicit cache metadata, removes stale objects, invalidates
CloudFront, and smokes the distribution hostname. The committed config remains
the direct endpoint used by local development.

## Continuous deployment

Every merge to `main` first runs `.github/workflows/validate-main.yml`: a
high-severity `npm audit`, non-browser verification, and—when browser code can
change—the sharded Chromium suite plus the tagged cross-browser deployment
smoke. Validation is safe to cancel when a newer push arrives; the replacement
classifies the cumulative diff since the last successful production run. What
each quality gate contains is documented in `CONTRIBUTING.md`.

A successful validation triggers `.github/workflows/deploy.yml`, which requires
that exact SHA still to be `main` and serializes production work. API/infra-only
changes run `npm run deploy:api` and the API smoke without publishing the web
build. Web and shared-package changes first update the API's referee
`WEB_VERSION`, smoke the API, build once, and then publish the AWS web copy with
`/api`. Test-only, fixed-host, tooling, and documentation changes stop after
validation. This keeps
incompatible web and Lambda versions from reaching production without paying
for an unrelated surface on every commit. A validated SHA superseded while it
waits for the production lock ends as a successful no-op and writes no production
marker, so routine rapid pushes do not produce false failure notifications.

Lambda artifacts use a SHA-256 content key. Re-running an identical bundle does
not invent a new S3 key or force a Lambda publication, and CloudFormation's
"No updates" response is a successful no-op. The website emits an uncached
`version.json`; stale tabs poll the web-host-owned manifest rather than treating
player API reachability as a web-version signal.

GitHub Actions holds no AWS key (2026-09-26). The promotion job runs in the
`production` environment, which admits only `main` with no admin bypass, and
assumes the `elixir-drop-github-deploy` role with GitHub's OIDC token
(`ELIXIR_DROP_DEPLOY_ROLE_ARN` variable). The role trusts only this repository's
`production` environment (`infra/scripts/deploy-identity.mjs`, created by
`bootstrap.mjs`) and carries the `elixir-drop-deployment` grant. The
`elixir-drop` user and its `.env` key remain for the Control Room's referee
role only. Region, CloudFormation role, code bucket, and stack name are
repository variables. The non-secret ACM ARN is another variable. Session-signing
and other application secrets are in the runtime secret, so neither CI nor the
stack carries them. (If a
`ELIXIR_DROP_FASTMAIL_JMAP_TOKEN`, `ELIXIR_DROP_BUTTONDOWN_API_KEY` or
`ELIXIR_DROP_BUTTONDOWN_NEWSLETTER_ID` repository secret still exists from an
earlier setup, delete it.) The pull-request gate and the daily exhaustive browser regression
run through `.github/workflows/verify.yml` with no secrets at all — fork-safe by
construction.

The first stack creation remains a local `npm run deploy:api` operation, run as
`AWS_PROFILE=cloud-engineer` with the mode-0600 root `.env` supplying settings
(never its AWS key); `elixir-drop-runtime` must exist first. Rotating a
credential needs no deploy ("Runtime secret" below). A local deploy
refuses unless the checkout equals `origin/main` and its tree passed
`validate`; `--break-glass` skips that check for an outage.

### Runtime secret

Drop's credentials live in one Secrets Manager secret, `elixir-drop-runtime`: a
JSON object whose keys are the env names `SESSION_SECRET`, `TELEMETRY_PEPPER`,
`ELIXIR_DROP_UPDATES_PUBLISH_TOKEN` and `ELIXIR_OAUTH_CLIENT_SECRET`. Drop's
Elixir integration key (`ELIXIR_INTEGRATION_KEY`, legacy `ELIXIR_MCP_KEY`) was
retired on 2026-11-13; no function reads those names, so they can be deleted
from the secret at any time. Jamie keeps it by hand in the console; the
stack does not own it and no deploy writes it. Only the API and
result-consumer roles may read it (never the refresh worker, the referee role,
CI, or the browser).
No stack parameter or function environment carries a credential, so no function
configuration or retained Web Function revision holds a copy (since 2026-11-04).
The functions get only `RUNTIME_SECRET_ID`; `services/api/src/runtime-secrets.ts`
reads the secret once per container before the first config read and logs
`runtime_secrets.loaded` with key names only (`fromSecret`, `absent`). Other
names in the secret are ignored, and non-secret settings stay in the function
environment.

The load fails closed. A secret that cannot be read or parsed, or one missing a
name that function needs, logs `runtime_secrets.load_failed` with names only and
throws. The API needs all four and answers 500 on everything but `/health`.
Refresh holds no credential and does not read the secret. The result consumer
needs `SESSION_SECRET` and `TELEMETRY_PEPPER`, which its shared `getConfig()`
requires, and throws without them, so SQS retries the message and then moves
it to the dead-letter queue. A failed load is not cached, so a brief outage clears on
the next request or message. An environment value never stands in for a missing
name.

**An edit to the secret takes effect at the next cold start**, not at a deploy
and not at once. Running containers keep the values they loaded, so old and new
values overlap until those containers are replaced, and a wrong value appears
only when a new container reads it. A deleted or blanked key takes that
function down at its next cold start, so remove a key only after a change that
stops requiring it has deployed.

To rotate a credential:

1. In the console (us-east-1): Secrets Manager, `elixir-drop-runtime`, Retrieve
   secret value, Edit, Key/value. Change the value, keeping the name exact, and
   save.
2. For `ELIXIR_DROP_UPDATES_PUBLISH_TOKEN`, also change the fixed host's `.env`,
   which publishes with its own copy. Publishing can fail while old and new
   containers overlap.
3. Read `runtime_secrets.loaded` and `runtime_secrets.load_failed` in
   `/elixir-drop/api` and `/elixir-drop/refresh` after the edit. The log shows
   names, not whether a value is right, so check the credential's natural use as
   well (sign-in, hub reads, a publication).

To back out a bad edit, restore the earlier value in the console, or move the
`AWSCURRENT` label back to the `AWSPREVIOUS` version.

Rolling back the removal of the parameters is not a plain revert. The stack no
longer stores them, so a reverted deploy asks CloudFormation for the previous
value of `SessionSecret`, `TelemetryPepper` and `UpdatesPublishToken`, which do
not exist, and CI has no values to send. Prefer a forward fix. If the old shape
is truly needed, deploy the revert locally with those three names in the
environment; the root `.env` does not hold `TELEMETRY_PEPPER`, so that value has
to be supplied by hand and removed afterwards.

A stack-level tag change is not a no-op: CloudFormation updates every
taggable resource, and some handlers re-put their whole configuration. On
2026-09-24 a tag-only update reached the API stage's access log, which needs
`logs:CreateLogDelivery` and its siblings on `*`; the execution role lacked
them, so the update and its rollback both failed (UPDATE_ROLLBACK_FAILED)
until 25f0f86. Before a tag or other stack-wide change, compare the execution
role's grant with every resource type in the template.

CloudFormation owns the private web origin and CloudFront distribution as well
as the API, refresh queue and worker, and retained season-repair channel. The
default static behavior uses AWS's managed combined CORS and security-headers
policy (chosen when Drop's retired Buttondown archive loaded the app font), so
every static response receives HSTS, content-type, framing, and referrer
protections; `/api/*`, `/share/*`, and `/share-assets/*` keep the API's own
response and cache policy.

The distribution uses the account's shared AWS WAF web ACL (`edge`, owned by
projects-sysadmin's `edge-waf` stack) through
`WebACLId: !ImportValue edge-waf-WebAclArn`; its rules count only until tuned.
CloudFront reads the web ACL as the caller on every distribution update, so the
stack-owned `elixir-drop-edge-web-acl` policy (and bootstrap, for a fresh
environment) grants the execution role `wafv2:GetWebACL` on that one web ACL.

## Background refresh

The HTTP deployment ZIP contains bundled `index.js` and its package metadata.
A separate content-addressed event ZIP contains `refresh-worker.cjs`,
`cr-results.cjs`, `run-analysis-job.cjs`, and the CloudFormation origin-policy
provider. The provider
owns policy create/update/delete because the native policy resource schema does
not yet admit Web Function ARNs; it has no application secrets or data access. The stack provisions a separate refresh FIFO
queue, DLQ, worker role and Lambda. API requests may send work; only the worker
consumes it. The worker has table access only: it advances Drop's own season
clock and season posts, and holds no secret, Elixir URL, sign-in, mail,
S3 publication or referee-correlation credential.

The worker processes one message per invocation with concurrency capped at two.
FIFO groups serialize the clock and each player; duplicate jobs within five
minutes coalesce. The 720-second visibility timeout is six times its 120-second
execution timeout. Failed jobs retry up to five receives before entering the
14-day DLQ. The queue-age alarm uses the existing operator alarm topic.
Inspect `/elixir-drop/refresh` for safe errors and `api.timings` operation data;
replay failed refresh work only after correcting its cause. Public requests retain
cached responses during worker outages. Queue enqueue failure is logged and the
next ordinary request retries it.

## HTTP deployment and removal of the old transport

CloudFormation owns the function, immutable revision, weighted endpoint, OAC,
origin policy, logging, and code-bucket read policy. The endpoint references the
revision explicitly; a deployment replaces the revision, moves routing, then
removes the old revision. Configuration changes are revision changes. Identical
artifacts/config remain a no-op. Worker and HTTP artifacts are separate.

`ApiUrl` is the canonical CloudFront `/api` URL, `ApiOriginDomain` is the private
origin, and `ApiRevisionId` identifies the served revision. Local dev config and
operator tools use the canonical URL. Production smoke checks CORS, bearer
refusals, origin denial, and public reads; successful guest runs are tested in
fixtures or isolated resources, never synthesized on production.

The HTTP API Gateway, routes, integration, stage, invoke permission, former
HTTP Event Function and access-log group are removed. There is no origin marker
parameter or CI secret dependency and no Gateway event adapter in the source.
Rollback is a reviewed revert through the normal validated deployment path;
stateful table and share data are retained.
